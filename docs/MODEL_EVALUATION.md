# Model Evaluation — Curriculum Retrieval and Activity Generation

**Subsystem 3 (UC3), DAS D.I.A.L.**
Measured 7–8 August 2026 against the live corpus of 264 `lesson_plan` chunks.
Harness: `backend/evals/`, `backend/scripts/calibrate_gate.py`.
Raw results are written to `backend/evals/results/` but are **not tracked in git** — they are
regenerated by re-running the commands in §10. The harness and the golden set are tracked, which is
what makes any figure here reproducible.

---

## 1. Executive summary

| # | Finding | Status |
|---|---|---|
| 0 | **The live system currently admits 2 of 7 junk queries through its similarity gate** | **Reproduced** — actionable now |
| 1 | `gemini-embedding-001` outperforms the newer `gemini-embedding-2` on every retrieval metric, because `-2` silently ignores `taskType` | **Strong evidence** — 240 probes |
| 2 | `nomic-embed-text` **ranks better** than `gemini-embedding-001`, but separates junk from real **21× worse**. Staying on nomic **provisionally**, pending the prefix experiment | **Measured** — a genuine trade-off, §5 |
| 3 | Guardrail 2 (model self-refusal) catches **1 of 8** off-topic requests, identically on two vendors | **Strong evidence** — 3 independent runs |
| 4 | Similarity gates: **0.71** for `gemini-embedding-001` (margin 0.041), **0.67** for `nomic-embed-text` (margin 0.002) | **Measured** |
| 5 | `gemini-3.5-flash` vs `claude-sonnet-5` for generation | **Inconclusive** — variance exceeds the difference; Sonnet dropped on cost |

The central practical result is Finding 0 read together with Finding 3. The similarity gate is the
system's **only** working defence against off-topic generation — the refusal guardrail that was
assumed to back it up does not function — and at its current setting that gate is too loose. Two
deliberately off-topic queries pass it today.

Finding 2 is the awkward one: the incumbent model is *better at ranking* and *much worse at
refusing*. Because of Finding 3, refusing is the property that carries the risk.

## 2. What was measured, and how

Three separate instruments, deliberately kept apart because they answer different questions and have
different reliability.

| Instrument | Question | Labels | LLM involved? |
|---|---|---|---|
| **A. Self-retrieval benchmark** | Which embedding model ranks better? | automatic (each chunk is its own answer) | no |
| **B. Golden-set retrieval eval** | How good is retrieval on realistic requests? | 28 hand-authored cases | no |
| **C. RAGAS + refusal check** | Is the generated activity grounded? Does it refuse? | 20 in-domain cases | yes — `claude-opus-5` judge |

**Instrument A** builds a pseudo-query from each chunk's own title + concept + stage (never its body),
ranks all 264 chunks, and records where the source chunk lands. 240 of 264 chunks have a title and
were usable. No metadata filters, no keyword fusion — this isolates the embedder.

**Instrument B** uses `backend/evals/golden_queries.yaml`: 20 in-domain cases, 7 deliberately
out-of-domain "junk" cases, and 1 Band C case that must return nothing. Queries mimic the real
output of `ActivityGenerationService.build_query` — short and numeric-heavy, e.g.
`"literacy activity targeting phonics 2.4/10 - recognising and producing rhyme"` — because that is
the string distribution the system actually sends.

**Instrument C** runs the real retrieval-and-generate path, then scores with RAGAS. The judge is
`claude-opus-5`, deliberately a **different vendor from the generator**: LLM judges systematically
prefer output from their own family, so a Gemini judge scoring Gemini output would inflate
faithfulness by an unmeasurable amount.

### Corpus profile

| Property | Value |
|---|---|
| `lesson_plan` chunks | 264 (of 279 total rows) |
| Band A / B / C | 115 / 149 / **0** (Band C parser is a stub) |
| `embed_text` length (chars) | min 285, median 1212, p90 2316, max 6245 |
| Largest chunk in tokens | ~1561 |
| Chunks exceeding 2048 tokens | **0** |

That last row decides Finding 1's main counter-argument — see §3.3.

## 3. Finding 1 — `gemini-embedding-001` beats `gemini-embedding-2`

### 3.1 The mechanism: `-2` accepts `taskType` and ignores it

Retrieval is an **asymmetric** task: a short query and a long document should be encoded differently.
Both models advertise `RETRIEVAL_QUERY` and `RETRIEVAL_DOCUMENT` task types. Only one honours them.

Probing the live API with the same text encoded both ways:

| Probe | `gemini-embedding-2` | `gemini-embedding-001` |
|---|---|---|
| `cos(QUERY, DOCUMENT)` on identical text | **1.000000** — vectors are identical | 0.873322 — genuinely different |
| Invalid `taskType` value | HTTP 400 | HTTP 400 |
| L2 norm at 768 dims | 1.000000 (auto-normalised) | 0.589572 (**not** normalised) |

`-2` validates the field and then discards it. Google's documentation hints at this — it describes
`-2` as taking task type "via prompt instructions" while `-001` takes the enum — but the API returns
`200 OK` either way, so nothing signals the difference at runtime.

> **Transferable lesson.** Never assume a task-type parameter is honoured because the request
> succeeded. Encode one string both ways and compare the vectors. A validated-but-ignored parameter
> is indistinguishable from a working one without this check.

### 3.2 The effect: measurably worse retrieval

Instrument A, 240 probes over 264 chunks, identical inputs and procedure for both models:

| Metric | `gemini-embedding-2` | `gemini-embedding-001` | Δ |
|---|---|---|---|
| MRR | 0.6130 | **0.6972** | +13.7% rel. |
| recall@1 | 0.429 | **0.533** | +24.2% rel. |
| recall@3 | 0.742 | **0.829** | +11.7% rel. |
| recall@10 | 0.925 | **0.971** | +5.0% rel. |
| Gate window (real p05 − junk max) | +0.1414 | **+0.2072** | +47% rel. |

`-001` wins on every metric in the same direction. The effect is consistent with the mechanism in
§3.1 — `-2` structurally cannot do the thing that produces the separation.

### 3.3 The counter-argument, and why it does not apply

`-2`'s genuine advantage is an 8192-token input window against `-001`'s 2048. On a corpus with long
documents this would matter. **On this corpus it is irrelevant: the largest chunk is ~1561 tokens and
zero chunks exceed 2048.** The advantage is unreachable.

### 3.4 Decision

Between the two Gemini models, `gemini-embedding-001` at 768 dimensions (Matryoshka truncation) —
a drop-in for the existing `vector(768)` column and HNSW index, no schema migration. Because `-001`
is **not** auto-normalised at 768, vectors are L2-normalised in the provider before storage.

This settles *which Gemini model*, not *whether to use Gemini at all*. §5 compares the winner against
the incumbent `nomic-embed-text`, and that comparison is less one-sided.

## 4. Finding 0 — the live gate is too loose today

`MIN_SIMILARITY` refuses a request *before* spending an LLM call when the best retrieved chunk is too
weak to ground an activity. The live system runs `nomic-embed-text` with the default
`MIN_SIMILARITY = 0.50` (no override in `.env`).

Measured junk scores under that exact configuration:

| Out-of-domain query | Score | Passes the 0.50 gate? |
|---|---|---|
| `junk_router` | 0.4119 | no |
| `junk_tax` | 0.4227 | no |
| `junk_medical` | 0.4286 | no |
| `junk_travel` | 0.4358 | no |
| `junk_recipe` | 0.4440 | no |
| `junk_football` | 0.5458 | **YES** |
| `junk_maths_lookalike` | 0.6686 | **YES** |

**2 of 7 deliberately off-topic queries clear the gate.** Guardrail 2 then catches roughly 1 in 8
(§6). So a request such as *"premier league fixtures this weekend"*, scoped to a learner's band, will
in most cases produce a fully-formed literacy activity built from whatever chunks ranked highest.

The 0.50 default was tuned to an earlier reading of nomic's band (junk ≈0.42, real ≈0.58+). The junk
ceiling measured here is 0.6686 — well above that assumption. The immediate fix is to raise the gate;
the measured recommendation for nomic is **0.67** (§5.3), though see the margin warning there.

## 5. Finding 2 — incumbent vs challenger: a genuine trade-off

Both models scored on the **same 28-case golden set** (`golden_digest ffef2baba8fd`), same k=3, same
hybrid RRF retrieval, same corpus. Only the embedding model differs.

### 5.1 Ranking quality — `nomic-embed-text` wins

| Metric | `nomic-embed-text` (incumbent) | `gemini-embedding-001` (challenger) | Δ |
|---|---|---|---|
| recall@3 | **0.6875** | 0.6000 | −12.7% rel. |
| precision@3 | **0.4833** | 0.4167 | −13.8% rel. |
| hit_rate@3 | **0.8500** | 0.8000 | −5.9% rel. |
| MRR | **0.8167** | 0.7250 | −11.2% rel. |
| nDCG@3 | **0.7053** | 0.6216 | −11.9% rel. |

The challenger is **worse at ranking on every metric**. This directly contradicts the expectation set
by MTEB leaderboards and by the `-001`-vs-`-2` result in §3, and it is worth stating plainly rather
than burying: on this corpus, for these queries, the small local model retrieves better.

Two things make the result more striking, not less:

- nomic is running **without** its required `search_query:` / `search_document:` prefixes (open item
  #7), i.e. handicapped, and still wins.
- nomic is 137M parameters running locally at zero marginal cost.

### 5.2 Junk separation — `gemini-embedding-001` wins decisively

| Population | `nomic-embed-text` | `gemini-embedding-001` |
|---|---|---|
| In-domain min | 0.6705 | 0.7268 |
| In-domain median | 0.7504 | 0.7621 |
| Junk median | **0.4358** | 0.5116 |
| Junk max | 0.6686 | 0.6859 |
| **Gate window** (real min − junk max) | **0.0019** | **0.0409** |

nomic's window is **0.0019** — about two thousandths. That is not a safety margin; it is a
coincidence. A single new adversarial query landing two thousandths higher would make *no* threshold
able to separate junk from real content.

`gemini-embedding-001`'s 0.0409 is 21× wider. Still thin in absolute terms, but it is a margin.

### 5.3 Calibrated gates

| Model | Recommended `MIN_SIMILARITY` | Margin | Verdict |
|---|---|---|---|
| `nomic-embed-text` | 0.67 | 0.0019 | technically separable, practically fragile |
| `gemini-embedding-001` | **0.71** | 0.0409 | usable |

In both cases the junk ceiling is set by the same single case, `junk_maths_lookalike` — phrased in
the system's own template: *"literacy activity targeting phonics 3.0/10 - long division and
multiplying fractions"*. Excluding it, both windows look comfortable (nomic 0.12, Gemini 0.19).
Including it, one is fragile and one is merely thin.

**That case is the realistic failure mode**, not the tax-return query: a therapist asking, in the
system's own phrasing, for something the corpus does not cover.

### 5.4 How to weigh this

The two models are better at different things, so the choice depends on which failure costs more:

- **Retrieving a slightly less apt chunk** (nomic is ~0.09 better on recall@3) yields a marginally
  weaker but still grounded, still band-appropriate activity.
- **Failing to refuse an off-topic request** yields a confident, plausible activity that answers
  something the curriculum never covered — and per §6 nothing downstream will catch it.

Given that Guardrail 2 does not work, the second failure has no backstop and the first degrades
gracefully. On that reasoning `gemini-embedding-001` is the safer default **despite ranking worse**.

This is a judgement call, not a measurement, and it is reasonable to decide otherwise — particularly
because nomic has an untested upside: its task prefixes are missing (open item #3), and adding them
could improve both its ranking *and* its separation.

### 5.5 Decision taken — `nomic-embed-text`, provisionally

**The project stays on Ollama / `nomic-embed-text` for now**, i.e. the incumbent, which is the better
*ranker* and free to run. This deliberately does not follow the §5.4 reasoning, and the grounds are
that the trade-off is unresolved rather than resolved in nomic's favour: the prefix experiment
(open item #3) could improve nomic on both axes and settle the question outright, and running it
first avoids a migration that might then be reversed.

**This choice is provisional and should be reported as such.** Two consequences follow from it and
must not be dropped:

1. `gemini-embedding-001` vectors remain in `embedding_alt`, so switching later is a configuration
   change plus a re-derived gate — no code work, no re-embed.
2. The system is running on the model with the **0.0019** gate window, which makes open items #1 and
   #4 more pressing, not less.

## 6. Finding 3 — the refusal guardrail does not work

UC3 has two guardrails against generating from irrelevant material:

1. **Guardrail 1** — the `MIN_SIMILARITY` retrieval gate (refuses before the LLM is called).
2. **Guardrail 2** — the model self-refusing with `INSUFFICIENT_CONTEXT`, per `SYSTEM_PROMPT`,
   detected by `model_refused()`.

With Guardrail 1 bypassed so Guardrail 2 could be observed in isolation, across 8 off-topic requests:

| Generator | Refusals detected | Rate |
|---|---|---|
| `gemini-3.5-flash` | 1 / 8 | 12% |
| `claude-sonnet-5` | 1 / 8 | 12% |

Reproduced **three times** across separate runs, with the same result each time. In every case the
single refusal was `c_empty_band` — Band C, which retrieves zero chunks, so the grounding block is
literally empty.

Given valid curriculum chunks and an unrelated request, both models write a competent activity from
the chunks rather than refusing. Example first lines for the query *"how do I file my income tax
return this year"*:

- `gemini-3.5-flash` → `### Activity: Game: Say Out a Sentence!`
- `claude-sonnet-5` → `# Learning Activity: Punctuating Paragraphs — Fast Food & Directions`

**Two frontier models from different vendors producing an identical rate means this is a prompt
problem, not a model problem.** In `SYSTEM_PROMPT`, the instruction *"use ONLY the grounding
activities provided"* reliably beats *"if the grounding activities do NOT cover the request, reply
`INSUFFICIENT_CONTEXT`"*. Swapping the generator will not fix it.

### Consequence

Guardrail 2 is not a backstop. `MIN_SIMILARITY` is effectively the **only** defence against
off-topic generation. Any proposal to loosen that gate has nothing behind it.

### Secondary risk found in the same area

`model_refused()` matches the sentinel on the **first line only**, and
`model_refused("")` returns `False`. A safety-blocked or empty completion is therefore persisted as an
activity with empty content. Not triggered in these runs, but latent on the service path.

## 7. Finding 5 — generator choice is inconclusive; Sonnet dropped on cost

Judge `claude-opus-5`, `max_tokens=8192`, 20 in-domain cases:

| Metric | `gemini-3.5-flash` | `claude-sonnet-5` |
|---|---|---|
| faithfulness | 0.7767 | 0.8312 |
| context precision (LLM, no reference) | 0.8750 | 0.9083 |
| context recall (non-LLM) | 0.5667 | 0.5667 |
| refusal detection | 1/8 | 1/8 |
| median output length (chars) | 2584 | 2785 |
| mean output length (chars) | 2383 | 2640 |

### Why this does not support a conclusion

Claude leads faithfulness by **0.055**. But an earlier run of the *same* Gemini configuration scored
**0.9000**, against 0.7767 here — a within-model swing of **0.123**, more than double the
between-model gap.

Generation is not deterministic on either provider (Gemini's seed is best-effort and only when
explicitly passed; Claude 5 has no seed parameter and rejects `temperature` outright), so every run
re-generates all 20 activities. With n=20 and unquantified variance, **a 0.055 difference is noise.**

> **Do not report `claude-sonnet-5` as more faithful than `gemini-3.5-flash` on this evidence.**
> To make the comparison, run each generator 5–10 times and compare distributions, not point
> estimates.

`context_recall` is identical (0.5667) for both, as it must be — it scores retrieval, which is
unchanged between generators. That serves as an internal consistency check on the harness.

### Decision: `gemini-3.5-flash`, on cost

**`claude-sonnet-5` was dropped for budget reasons** after the evaluation period incurred ~US$18 of
Anthropic spend. Since the quality comparison is inconclusive, there is no measured quality argument
against this: the evidence does not show `gemini-3.5-flash` to be worse, and it is already
configured, needs no second provider, and produced ~11% less output by mean character count (2383 vs
2640 over 20 activities).

That is an argument from *absence of demonstrated difference*, not a demonstration of equivalence.

> ### ⚠️ The US$18 is mostly the RAGAS **judge**, not Sonnet generation
>
> This distinction matters for any conclusion drawn from the figure, and it is easy to get backwards.
>
> | | Model | Approx. calls | Runs in production? |
> |---|---|---|---|
> | RAGAS judge | `claude-opus-5` | ~60 scoring jobs **per evaluation**, over several evaluations — including runs wasted on the harness defects in §9 | **No** — eval-only |
> | Sonnet generation | `claude-sonnet-5` | ~64 total | Would have |
>
> The judge is the larger consumer by a wide margin, uses the more expensive model, and never runs
> in production. **The eval spend is therefore not the cost of running Sonnet as the generator**, and
> should not be quoted as such.
>
> If evaluation cost needs controlling, the lever is the judge — its model, its run frequency, or the
> number of metrics — not the generator. This matters directly for the deferred 10× benchmark
> (open item #8), which would multiply judge calls tenfold.

Per-request cost was **not** instrumented. The US$18 is an account-level total across the whole
evaluation period, not a per-activity rate, and per-token rates should be read from each vendor's
current rate card rather than assumed.

`ClaudeProvider` remains in the codebase and registered in `COMPLETION_PROVIDERS`. Dropping Sonnet is
a configuration choice (`LLM_PROVIDER`), not a code removal, so the A/B can be repeated later at no
engineering cost.

## 8. Threats to validity

Stated plainly, because several of these bound how far the numbers above can be pushed.

**1. The incumbent runs handicapped.** `nomic-embed-text` requires `search_query:` /
`search_document:` task prefixes and the current code sends raw text, so the §5 baseline measures
nomic *below its own ceiling*. It is the honest incumbent number — it is what production does today —
but it is not nomic at its best, and it should not be presented as such. Since nomic already wins on
ranking, the upside is untested and could change the §5.4 recommendation (open item #7).

**2. The golden set is a draft and its labels depress recall.** `golden_queries.yaml` was authored by
reading the ingested corpus, not by a curriculum specialist. All four "misses" in the golden-set eval
were inspected and every one is a labelling artefact:

| Case | Diagnosis |
|---|---|
| `b_when_expander` | **Label is wrong.** Labelled a single "Examples for..." page in `19) Sentence Mobility.pdf`; retrieval correctly returned three chunks from `15) When expander.pdf`, a document dedicated to the concept. Retrieval beat the ground truth. |
| `b_subject_describer` | Returned near-identical chunks from the same file, different instances. Arbitrary choice among 54 `subject` chunks. |
| `a_action_predicate_intro` | Returned adjacent chunks, same document and concept, different pedagogical stage. |
| `b_barebone_sentence` | Same document and concept, `production_activity` rather than the labelled `presentation`. |

Labels were **deliberately not corrected**, because rewriting ground truth to match system output
destroys the eval's independence. **Every recall figure in this document is therefore a floor, not an
estimate** — including both models' in §5.1. Three of the four misses above are shared by both
models, so the comparison between them remains fair; only the absolute values are depressed.

Note also that `recall@3` is capped by k: a case with 4 relevant chunks scores at most 0.75 with
k=3. This is a property of the system (only k chunks reach the model), not of the metric.

**3. Instrument A is a proxy.** Self-retrieval measures whether a model can match a chunk's metadata
to its content — not whether it finds what a therapist wants. It is fair *between models* (identical
inputs, identical procedure) but its absolute values are not production numbers: it applies no
metadata filters and no keyword fusion, both of which the real pipeline uses.

**4. Variance is unquantified.** One generator was run twice; every other configuration was run once.
See §6.

**5. Junk cases are few.** Seven out-of-domain queries, of which one dominates the gate margin. A
larger adversarial set would give a more trustworthy threshold.

**6. Data quality issue found incidentally.** The `stage` column carries parser leakage — roughly 45
of 264 chunks hold values such as `'name of activity: choc-a-sound objective:'` or
`'name: ____ date: ____'` instead of a pedagogical stage. Since `filter_stage` is a hard `WHERE`
clause, those chunks are unreachable by any stage-filtered query. Not caused by this work; out of
scope for it; worth fixing in ingestion.

## 9. Harness reliability notes

Three defects in the harness itself were found and fixed during this work. They are recorded because
each produced *plausible-looking output while measuring nothing*.

| Defect | Symptom | Fix |
|---|---|---|
| Judge never authenticated | `ChatAnthropic` reads `ANTHROPIC_API_KEY` from `os.environ`, but the app loads `.env` via pydantic-settings, which does not export it. Every LLM metric returned `nan`; the run still exited 0. | Pass the key explicitly; `SystemExit` if missing |
| RAGAS sends `temperature` | `LangchainLLMWrapper` hardcodes `temperature` into every judge call; Claude 5 rejects it with HTTP 400 (deprecated, not ignored). | `_NoTemperatureWrapper` subclass mirroring ragas 0.2.6's own branch minus that argument |
| Judge budget too small | One truncated statement-decomposition raised `LLMDidNotFinishException`; RAGAS takes a plain mean, so **one failed sample `nan`-ed all 20 scores**. | `max_tokens` 2048 → 8192 |

A guard now prints `!! NO MEASUREMENT for: <metric>` whenever a metric is `nan`, stating explicitly
that it is missing data and not a low score. **A `nan` faithfulness read as zero looks like
catastrophic hallucination; read as fine it hides a broken harness.** Neither reading is acceptable.

## 10. Reproducing these results

```bash
cd backend

# --- retrieval, per embedding model (deterministic, no LLM) ---
# challenger: gemini-embedding-001, vectors in embedding_alt
python -m evals.run_retrieval_eval --provider gemini --column embedding_alt
python -m scripts.calibrate_gate   --provider gemini --column embedding_alt

# incumbent: nomic-embed-text, vectors in embedding (needs `ollama serve`)
python -m evals.run_retrieval_eval --provider ollama --column embedding
python -m scripts.calibrate_gate   --provider ollama --column embedding

# --- generation (needs .venv-eval; see requirements-eval.txt) ---
python -m evals.run_ragas --generator gemini --refusal-only        # no ragas install needed
python -m evals.run_ragas --generator gemini --judge claude-opus-5
python -m evals.run_ragas --generator claude --judge claude-opus-5   # Sonnet: dropped, see §7
```

`--provider` and `--column` **must** agree: embedding a query with one model and ranking it against
another model's stored vectors returns confident nonsense rather than an error.

Results are written to `backend/evals/results/*.json`, each carrying a `golden_digest`. **Two result
files are comparable only if their digests match** — that is what proves both runs scored the same
cases. The document side is replayed from the stored `embed_text` by
`scripts/reembed_curriculum.py`, so re-embedding never changes the text being compared.

`requirements-eval.txt` must be installed into a **separate virtualenv** (`.venv-eval`): installing it
alone into the app venv downgrades numpy to 1.26.4, below the `numpy==2.1.1` pin that
`scikit-learn==1.5.2` depends on.
